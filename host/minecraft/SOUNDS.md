# Sound definitions, selection, and audio custody

The five selected Java releases have matching bounded weighted-selection observations, including aggregate overflow and repeated callback reads. Their selected sound decoder also accepts some numeric values after integer conversion that differ from their raw JSON value. These are separate contracts from event registration, resource presence, audio decoding, channel allocation, and audible playback. This family remains partial.

The [source map](sound-sources.json), regenerated by [sound_sources.py](sound_sources.py), attributes 59 private Java inspection views and five Polytone views to original class bytes. Six older audio-library classes have identities but no inspected view in this map. Source locators are not a complete grammar, a verified decompilation, or a transitive effect proof. Original source, binaries, and user installations remain private.

Device selection, listener state, category/master gain, subtitles, accessibility, device loss, and streamed playback remain independent consumer work. Bedrock remains a separate edition lane.

## Original-method and numeric observations

[SoundProbe.java](SoundProbe.java) calls the original `WeighedSoundEvents` with authored `Weighted` callbacks. It delegates draws to the original seeded `RandomSource`, records the actual bound and draw, and returns null from authored selection callbacks. Authored preload callbacks ignore the supplied null engine and can fail after recording an effect. No actual selected `Sound` is played.

The [Lean model](Sounds.lean) has ten laws, and [Bend](Sounds.bend) has six. They reuse the [Java word contract](../java/WORD32.md). Both predict 22 weighted-control cases per release: **110 comparisons** across 1.21.1, 1.21.4, 1.21.5, 1.21.11, and 26.3. The [case decoder](SoundsCase.lean) admits only the declared small fixture domain. The [pure replay](sound_conformance.py) checks nine research-decoder refusals and five changed observations. It consumes recorded random draws; it does not verify the random-number generator.

- Two individually positive weights `2147483647` and `1` produce a negative aggregate. The original random bound call rejects it with `IllegalArgumentException`.
- Four individually positive weights `1073741824` produce zero and take the empty-sound branch without drawing.
- Selection reads weights to calculate the aggregate, then reads them again while traversing. Authored changing callbacks can change the selected entry or produce fallback. Reachability of those changing callbacks through normal vanilla definitions is not established.
- Preload visits all entries, including zero-weight authored controls, until an authored exception stops traversal. Earlier callback effects remain observed. This is not real buffer preloading.

Eleven extended decoder inputs per release add **55 independent calibrations**, checked against an authored Python conversion projection rather than a Lean/Bend Gson proof. Numeric `1.9` becomes 1; `4294967297` and `-4294967295` become 1. `2147483648` converts to a negative value and refuses; `0.9` converts to zero and refuses. String `"2"` and null refuse in these fixtures; absent weight defaults to 1. Positive entries that overflow in aggregate are individually accepted. This is a bounded conversion result, not a complete JSON-number grammar or cross-library theorem. The original core captures' three decoder cases are retained but not counted again in the 55 extended calibrations.

All accepted native runs use macOS arm64 and explicit Java 21 or Java 25 profiles, bounded heaps, and two processors. Their receipts record frozen producers, requests, mapped member bindings, actual class-load identities, separate raw streams, and absent owned process groups. Deliberate process exit ends the private bootstrap context; it is not proof that asynchronous built-in bootstrap work completed normally.

## Failed context and superseded fixture disposition

Two initial bare-context 1.21.1 runs reached four unexpected fallback errors. The diagnostic run identifies an initial `ExceptionInInitializerError` caused by an unbootstrapped built-in registry; later accesses see an erroneous class. These are fixture-precondition failures, not evidence of a Minecraft fallback defect or a missing library. Both original captures remain private and are excluded in the [disposition ledger](evidence/sound-exclusions.json).

A fresh VM with explicit version detection and built-in registry bootstrap succeeds. One successful 22-case intermediate run predates decoder calibration and remains superseded, without invalidating its scoped observations. The five accepted core captures freeze 22 weighted cases and three decoder cases each. Later decoder-only requests freeze eleven cases each. The expanded current plan does not rewrite or reattribute those older frozen requests.

## Provider boundaries and independent proposals

Polytone's sound-types manager parses CSV sound-event declarations during prepare, dynamically registers missing events before decoding enabled sound types, requests a SoundManager reload on apply, and unregisters custom IDs/reset tables later. Registration is not a sound file, a completed reload, audible output, or server authority. The direct type names five sound-event holders plus volume and pitch. Construction captures their values in the base sound type; retaining holder fields does not by itself make every consumer a live lookup.

Its forward-aware codec first tries the original lookup. A failed lookup becomes the empty optional only when the identifier belongs to the bundled `future_ids.txt` set, with an empty sound-event fallback in the caller. That set is loaded asynchronously from a bundled resource. It is not a queue of pending dynamic registrations, and it does not promise eventual resolution of missing gameplay data. Sound-type reference/copy alternatives, block consumers, overlapping providers, reset ordering, and actual reload completion remain pending qualification. Modefite and Compat sound/resource-admission interactions also remain pending; absence of a dedicated sound hook is insufficient to declare them unaffected.

Independently selectable choices for a possible combined provider are:

- Keep the selected conversion and selection behavior when compatibility requires it, while diagnosing raw input, converted weight, and aggregate separately.
- Validate a positive bounded aggregate with wider/checked arithmetic before publishing an event. Define failure and prior-generation custody explicitly. This changes current boundary behavior and needs real registration/reference/pack tests.
- Require stable weights within one draw, or snapshot a complete event generation for selection. Callback mutability, recursive references, provider hooks, and retained consumers must determine the contract; the authored mutable control alone does not justify changing vanilla.
- Expose event admission, asset decode, device availability, preload completion, and playback as separate diagnostic states. A safe retry needs the actual failed stage and retained effects; an engine-started message alone cannot supply them.
- Bind cache entries, future disposal, stream ownership, channel use, and reload generations to explicit leases. This is a design obligation to investigate, not an implemented or verified replacement audio engine.

Run the retained comparison with `python3 host/minecraft/sound_conformance.py` after compiling models. Ordinary CI runs only that pure replay and formal checks. Owner-run collectors and source-map regeneration require existing private inputs and must not be substituted for a full client/provider test.
