# Working on rules

Rules is a research and verification repository. Start with README.md and the relevant model's explanation. A host contract, application-specific policy, executable model, proof, native observation, and proposal establish different things. Preserve their source identities, assumptions, counterexamples, and evidence limits.

## Ownership

Common rules live in common/. Host adapters and their receipts live in host/. Platform descriptions live in profiles/. Application studies have their own paths and owners. Agree shared write boundaries before editing. Keep active task continuation in the owner's task store, and maintain portable contracts in the repository.

Check the actual consumer when changing a shared predicate or codec. Preserve unsupported and unknown states. Revalidate drift before advancing a source pin. Never change a measured outcome or weaken a negative control just to obtain a pass. Record a contradicted expectation explicitly.

## Verification

Use the checksum-pinned development toolchain. Run scripts/check-rules.py for model changes and the relevant finite or native host comparison. See docs/development.md for commands and boundary coverage.

Ordinary CI checks formal rules, retained observations, and bounded host fixtures. Application launches, package-manager operations, external services, browsers, model inference, and sibling-project tests are owner-run evidence collection. They require a specifically selected local procedure and belong outside ordinary CI.

Coordinate graphical desktop access through re:desktop immediately before live desktop actions. Use isolated profiles and disposable fixtures. Keep all credentials, personal state, worlds, VM images, downloaded tools, and caches out of Git. Preserve attribution for retained third-party source.

## Contributions and commits

Use conventional commit subjects, such as feat:, fix:, test:, docs:, or chore:, with a concise lowercase description. Add a short body when it explains a consequential boundary or verification limit. Keep unrelated work and other writers' files out of the commit.

Use complete, plain prose and one owner per contract. Match terms across code, diagnostics, help, and documentation. Keep schema fields stable for callers and report partial outcomes and uncertainty accurately. Changes to serialized meaning, authority, or public guarantees need an explicit design rationale and migration plan.
