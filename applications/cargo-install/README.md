# Binary installation, ownership, and partial failure

This band studies Cargo 1.92.0 on macOS arm64 using one generated two-binary path crate and private installation, configuration, temporary, and target directories. It separates package registration, actual executable bytes, compilation, per-binary publication, cleanup, and removal authority. It reproduces a bounded registration inconsistency after a mixed new/replacement failure. It does not establish whether newer Cargo versions share that behavior.

The [source ledger](../sources/cargo-install-selections.json) pins Cargo revision `344c4567c634a25837e3c3476aac08af84cf9203`. Documentation and source agree that `--path` installs always build and reinstall; this fixture does not test registry/Git freshness skips. Tracking records include package source/version, selected binary names, build choices, target, and compiler provenance. They do not authenticate the bytes currently at a registered executable path.

## Collection and observations

The [collector](probe.py) uses the existing pinned Cargo/rustc with private `CARGO_HOME`, an explicit install root and target, offline mode, one build job, and incremental compilation disabled. The source has no dependencies. The target occupies 1,752 KiB; the original work tree measured 2,824 KiB before the small follow-up. No global tool, user installation, external registry, or empack build is changed.

The [initial setup refusal](../evidence/cargo-install-20261125T003303650622Z/setup-failure.json) found an ancestor Cargo configuration before launching Cargo or rustc. Its contents were not read. The corrected source lives outside that ancestor tree, under an owned `/private/tmp` directory. The failed producer is retained after refusal, without claiming it was frozen before that failed setup. The successful producer was frozen before its native commands.

The [main receipt](../evidence/cargo-install-20261125T003504421536Z/receipt.json) records 27 commands and six explicit file interventions. An independent [follow-up](../evidence/cargo-install-20261125T003504421536Z/new-bin-followup.json) records three more commands in a fresh private install root, reusing the compiled target and unchanged source. All owned groups retired. Commands, source/installation images, streams, original executables, and owned blockers are retained. Runtime stdout is checked independently of `cargo install --list`.

| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Mixed new/replacement counterexample

The fresh follow-up begins with an owned blocking directory at A and no B or metadata. `--force` permits the collision to reach publication. Cargo installs new B first, then fails to replace A with `Is a directory`. The captured stderr names those actions in that order. Both saved tracking formats then register B under v0.2, but the B path is absent. A and its marker remain unchanged.

Two subsequent processes independently read this result. `cargo install --list` succeeds and lists B. `cargo uninstall --bin rules-install-b rules-install-ownership` refuses with `corrupt metadata` because B does not exist. No harness mutation occurs between these three commands.

The selected source explains the mismatch. `Transaction.bins` records newly installed paths. The replacement loop saves its error, updates and saves tracking for successful binaries, then propagates the replacement error. Unwinding drops the transaction before `success()` can disarm it, removing new B after registration has been saved. Replaced existing paths are not in that cleanup list, which explains the earlier valid partial replacement without conflating the two cases. There is no syscall trace proving every intermediate boundary; the source order, command diagnostic, and independently captured final/readback images jointly support this scoped explanation.

This is a tracking-consistency defect in the tested version and controlled failure path, not a claim of a universally atomic installer. No upstream issue or product patch was made. Before an upstream fix proposal, check the current implementation and existing reports; these evidence pins are not a current-version claim.

## Models and proposals

The [Lean](Install.lean) and [Bend](Install.bend) models separate each fixture binary's body and exact package-owner token from the existence of tracking files. They preserve duplicate admission, path compilation, new-first publication, successful replacement prefixes, saved ownership, new-file cleanup, catalog scope, and all-owned-bin removal preflight. Twelve Lean and nine Bend laws include the observed counterexample and keep ordinary partial success separate.

The [pure replay](conformance.py) compares 30 command boundaries and six explicitly labeled interventions. For commands it compares both bin states, metadata presence, and status; interventions compare state without inventing a Cargo exit code. Version, lock-generation, and runtime commands are read-only installation observations here. The [observation checker](observations.py) separately verifies runtime stdout, both tracking formats, exact fixture identities, stream hashes, original source attribution, blocker preservation, and command/intervention continuity. Unknown bytes refuse classification rather than becoming absence. Thirteen malformed or out-of-scope research inputs refuse; six changed outcome fields are detected. The [conformance receipt](../evidence/cargo-install-20261125T003504421536Z/conformance.json) retains model inputs/outputs and evidence hashes. Replay invokes neither Cargo nor the fixture executables.

A separate pure candidate keeps successfully published new files once their partial ownership has been saved, while still returning the replacement failure. It differs from current behavior only in the observed mixed new/replacement case. This is a candidate ordering policy, not a native fix or universal consistency proof. A production correction must review earlier new-file failures, both metadata writes and their failure ordering, orphan removal, interruption, and transaction lifetime. Registering only surviving binaries is another possible design; keep-current without addressing the reproduced mismatch is insufficient if tracking consistency is the chosen requirement. Do not promise rollback of successful replacements merely because a command returns failure.

For empack, report completed per-resource effects separately from the command result, and make cleanup ownership consistent with the durable records that remain. Reuse existing operation/recovery machinery after reviewing its actual contract. This band does not justify a new general transaction framework, weaker file-ownership checks, or automatic adoption of changed executables. An installed-package list should describe registration unless it independently verifies current content.

Registry/Git acquisition and freshness, `--no-track`, foreign registered packages, arbitrary selection ambiguity, missing metadata, interrupted writes, concurrent installers, orphan removal, permission/race variants, Windows replacement, and broader install/uninstall semantics remain unqualified. The model admits successful staging and tracking writes and only the selected owned-directory rename failure. It refuses a selected directory-unlink branch instead of pretending the native API succeeded there.

The later [Cargo architecture review](../cargo/ARCHITECTURE.md) adds a separately collected `--no-track --force` failure: Cargo reports success and replacement while the blocker remains. The completion model treats that result path separately from this original tracked model's successful-metadata premise. It does not rewrite or broaden the original native observations.
