# Repository access keys and password-change scope

This band studies restic 0.20.0 on macOS arm64 with one new private local repository, one tiny backup, and generated passwords. It separates a password, its encrypted master-key wrapper, repository data, and the key used by a particular process. Successful access is a native observation; the models do not implement or prove the cryptography.

The [source ledger](../sources/restic-keys-selections.json) pins revision `9c88ff768f10c192dc6a87619a65a16374080e33`. `repository.AddKey` wraps the supplied existing master key with a newly derived user key, random salt, and nonce. The key file has its own content identity. `key add` creates and verifies another wrapper. `key passwd` creates and verifies a replacement wrapper, switches access to it, and removes the previously used wrapper. It does not generate a new repository master key. `key remove` refuses the wrapper used to open that process, even if other keys exist. These source facts are distinct from a cryptographic proof or a copied-key revocation experiment.

## Native sequence

The [collector](keys_probe.py) reuses the pinned binary with private home, cache, temporary directory, repository, and random password files. It freezes its producer and redaction helper before commands. Passwords, encrypted repository files, and raw user/host-bearing output stay in ignored work. Public observations contain file hashes and redacted CLI streams. No existing backup, credential, or user installation is opened or changed.

The [receipt](../evidence/restic-keys-20261125T005527819839Z/receipt.json) records 21 commands, all owned groups retired, and 216 KiB of generated work. After the initial backup, every non-key repository file retains the same path, size, and hash through the sequence. Three independent dumps return the exact saved marker. This establishes the measured byte/access scope without exporting a master key. The receipt's “no key export/decryption” limit means no explicit key export or manual decryption; ordinary restic access necessarily performs its own internal decryption.

| Boundary                                                       | Observed result                                                                                                     |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Initial key A                                                  | Its password opens the repository; listing identifies A as current for that process.                                |
| Add B with the same password                                   | Both wrappers remain. An explicit key hint selects A in the next list.                                              |
| Remove current A while B exists                                | Refusal with status 1; repository bytes are unchanged. Another available key does not waive current-key protection. |
| Change A's password                                            | New wrapper C replaces A; B remains. The new password opens C and the old password still opens B.                   |
| Read the existing backup through either password               | Both dumps return the same marker; encrypted data/config/snapshot bytes are unchanged.                              |
| Add using a wrong current password                             | Status 12; no repository mutation.                                                                                  |
| Add an empty new password without the explicit insecure option | Status 1; no repository mutation.                                                                                   |
| Open through B and remove C                                    | Success; C disappears. A subsequent process using C's password fails with status 12.                                |
| Remove sole remaining current B, or an unknown ID              | Each refuses with status 1 and unchanged repository bytes. B continues to read the marker.                          |

The [read-only observation checker](keys_observations.py) verifies command continuity, exact key-file identities, wrapper sets, non-key backing preservation, current-key JSON fields, dump bytes, source/tool identities, process records, and public/raw stream correspondence where private originals remain available. Fixture passwords are checked for accidental inclusion in public files without printing them. It does not treat a key's username/hostname label as an identity or authorization grant.

## Domain and interface decisions

Keep the existing distinction between adding an access wrapper, changing one wrapper's password, and removing another wrapper. Multiple wrappers are legitimate, including wrappers sharing a password. A successful password change therefore need not revoke all use of the former password. An application-wide password or true master-key rotation would have a different target, authority, cost, and compatibility contract. Removing a repository wrapper also does not establish revocation of master material already copied elsewhere; this is a source/design consequence, not an executed attack or current security audit.

The native current marker belongs to the process that opened the repository. Different hints can select different wrappers for the same password. It is not a persisted global “active key.” The finite model only uses observed exact hints or unambiguous fallback. General enumeration order, damaged wrapper behavior, key-search limits, and arbitrary fallback remain open.

A small reporting inconsistency is reproduced. The selected `key passwd --help` promises the new key ID, but stdout says `saved new key as <Key of …>` and describes the `Key` object without its full ID. The source passes that object to the formatter, whose `String()` implementation produces the description. This command and `key add` also use text printing under the captured global `--json`, while `key list` emits structured rows. This is current command-specific behavior, not evidence that all restic commands promise JSON.

A focused improvement is to return and print exact old/new wrapper IDs with the actual effect: “Changed password for key A; saved replacement C.” Keep the description as optional metadata, and explain that other keys are unchanged when relevant. Reuse existing `repository.Key.ID()` and command printers rather than creating a general credential-management framework. For machine callers, an explicit command-level result could carry the replaced and saved IDs and confirmed completion; changing JSON support needs documented output compatibility. Keeping the present key model and directing operators to `key list` is a valid architectural alternative, although the help/output ID mismatch should still be corrected. No product patch was made here.

Source ordering also leaves meaningful failure phases: a replacement can be created before verification or old-wrapper removal fails. A command failure is not automatically “the old password is the only one that works.” A future typed result or diagnostic should preserve confirmed wrapper changes and unknown cleanup; qualify those failure paths before promising atomic rotation. The native fixture does not inject these failures, interrupt a writer, or prove backend durability.

## Models and verification

The [Lean](Keys.lean) and [Bend](Keys.bend) models assign separate tokens to the three actual wrappers and controlled credential relations. They preserve current-key protection, single-wrapper password change, continued access through a duplicate password, failed authentication, empty-password admission, and removal of another wrapper. The non-key backing token represents independently equal captured file images, not master-key bytes. The general backing-preservation law describes this selected projection; it does not prove cryptographic preservation for arbitrary operations.

The [pure replay](keys_conformance.py) compares the 17 post-backup command boundaries with both models. Each compares wrapper membership, backing token, and status. Five list results additionally compare the actual current-key field; other returned current tokens remain source/model interpretation. Twelve Lean and nine Bend laws accompany eleven malformed/out-of-profile input refusals and six changed-outcome controls. The [conformance receipt](../evidence/restic-keys-20261125T005527819839Z/conformance.json) binds models, source selections, native streams, and the comparison masks. Replay executes no restic command and reads no plaintext password into model inputs.

Key derivation, authenticated encryption, randomness quality, arbitrary repository/key formats, hostile KDF parameters, damaged keys, search limits, interactive password entry, terminal handling, remote permissions, concurrent mutations, interrupted verification/removal, backup consistency, and copied-key compromise remain unqualified. For empack's design, preserve which key or wrapper an operation changes and what its completion establishes; encryption access wrappers and publisher signing keys must retain their different meanings and trust boundaries.
