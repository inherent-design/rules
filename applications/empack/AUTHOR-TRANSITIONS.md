# empack: adopting files and migrating a runtime

Adoption accepts an explicit description of files already present. Runtime migration proposes a different runtime and revalidates the project's selections. Neither restores a forgotten direct request merely because its locked content remains. These operations need separate input, preview, and result contracts even when they share preparation and publication machinery.

This is a source and test-body review at empack `0b4462e3032b4f09230b15329722eabefb7f574c`. The [source ledger](../sources/empack-author-transitions-selections.json) records exact Git blobs, hashes, and inspected ranges. No application, source-method comparator, engine test, or new formal model ran for this review. The [removal study](REMOVAL.md) already executes bounded core adoption/request-merging cases; that evidence does not qualify the native adoption workflow below.

The later [core admission comparison](author-transitions/README.md) now executes fifteen supplied-value adoption/validation calls and compares them with Lean and Bend. It distinguishes automatic and authored exact-pin policy, while demonstrating why matching runtime labels alone cannot establish provider compatibility. It does not turn this source/test-body review into an executed migration or observed-file workflow.

## Current adoption contract

| Boundary | Inspected behavior | Consequence |
| --- | --- | --- |
| Existing-lock selection | `adopt_with_services` parses logical keys, captures documents and selected dependencies, and requires a resolved project. | A title or foreign metadata filename is not the selected identity. A malformed or stale lock is not an invitation to create a replacement lock. |
| Provider identification | `observation::identify` reads bounded local files, asks the selected provider for an exact identification, and checks project identity, file role when supplied, and agreement across members. | Matching bytes for another project or role are insufficient. A latest-version guess cannot identify observed bytes. The provider/catalog implementation is a separate evidence boundary. |
| URL and world cases | Downloaded URL inputs become `ObservedUrl` at the selected placement. An existing provider world made entirely of archive members retains its exact archive selection instead of following the ordinary file-identification route. | Do not describe every adoption as a fresh provider hash lookup. World selection, live world bytes, and archive source evidence have distinct roles. |
| First lock | `initial::adopt` requires every declared root, rejects duplicate keys and search-only intent, and checks its resolution context. An unpinned provider needs explicit placements; a provider world needs its exact archive selection. | Adopting one convenient file cannot manufacture a complete first lock for unrelated unresolved authored roots. An empty resolver context is not the publication candidate. |
| Authored policy | `AdditionCandidate::prepare_adoption` binds an existing lock or uses initial adoption. Existing-lock core preparation restores current roots and adds a selected root only when its canonical installation was not already locked. Initial preparation retains existing authored roots. | Existing pins, constraints, and root/transitive roles remain meaningful. Observing a different version does not authorize silently rewriting an exact authored pin or promoting a retained transitive record. |
| Native capture and plan | Capture includes previous and proposed placements. `plan_adoption` verifies every selected proposed placement, rejects duplicates, and builds desired files only from intent/lock/binding documents. Its payload-content map is empty. | Adoption does not install missing files or rewrite game payloads. It can publish documents and create private preparation/recovery state; this is not a whole-host read-only operation. |
| Approval and execution | The host describes before/after resolutions and file changes, then passes its prepared operation to the existing application boundary. The API exposes an `AdoptObservedReceipt` with publication and project results. | Proposed metadata, user approval, document publication, and subsequent usability remain separate. A preview is not a receipt. |

The API request contains an `AdditionGroup`; the observed payloads must exist and satisfy that proposed description. It does not contain an arbitrary metadata import or permission to download replacement bytes. Its preparation route selects `UpdateSameIdentity`, while adoption's core policy still preserves authored constraints. Preserve both facts; an admission enum alone does not summarize the whole operation.

The native plan preserves the original lock document bytes when the candidate lock is equal. It may therefore produce no physical change after successful verification. An empty change list does not mean that no file was inspected, and a nonempty description does not prove that publication occurred.

## Current migration contract

`MigrationOptions::compose` requires and binds a current lock before editing candidate intent. It replaces the requested runtime but retains the authored preferred Java unless `--java` explicitly changes it. The target game's Java policy can refuse that retained preference. A recommendation assembled while parsing options is not permission to silently replace it during composition.

Each explicit provider replacement must name an authored provider root and a different canonical project. Only that root's source and selection change: its selection becomes automatic. Other roots and exact pins survive composition and must still be valid after resolution. Retaining a pin in a draft and establishing that it is valid for the target are different claims.

The sync host resolves the effective candidate, checks migration preparation against the original document/lock basis, and validates retained provider records when needed. Materialization and native preparation then produce a `SyncRequest::Migration` carrying the original `source_revision`, exact resolved candidate, evidence policy, and supplied content. This is not ordinary sync with a different printed heading, nor permission to adopt changed on-disk payloads.

The migration report combines semantic differences with the actual native preparation result. Its structured preview explicitly says `native_publication_performed: false`; a ready proposal is not an applied migration. Provider selection, declared compatibility, prepared native changes, materialized bytes, and a successful game launch have different evidence requirements.

## Proposed API and UX direction

Keep the current operation distinction. Share exact identity, captured revision, verified-content, prepared-operation, and publication-result machinery. Avoid a universal command that infers the desired policy from whichever files happen to exist.

- **Adoption request:** state which observed files and proposed exact description are being accepted. Preserve provider identification and authored-pin conflicts as explicit decisions. Explain missing bytes as a prerequisite failure; do not repair them by silently downloading during adoption.
- **Migration request:** state the target runtime, explicit Java decision, and explicit project replacements. Show preserved authored pins separately from target validation and locked selection changes. A retained library with incomplete requirements is not proven unrelated or garbage.
- **Preview and result:** distinguish verified observations, proposed document changes, proposed payload writes, blocked preparation, approval, publication, and uncertain execution. Derive text and structured output from those facts. A successful no-change verification and an applied document update deserve different outcomes.
- **Portable boundary:** a browser can retain an immutable observation and propose document edits. It cannot mint native-root identity, impersonate a provider, authorize a native write, or treat an imported plan as executable. Native preparation must own its fresh capture and authority.

For current empack, prefer these existing request types and small caller/report refinements over another resolver or migration framework. For the proposed 0.9 clean break, retain the same semantic distinctions in the project/image/work interfaces described by the [target model](README.md). These are design recommendations, not selected production changes or new wire schemas. Existing consumers and engine permission checks remain compatibility obligations.
