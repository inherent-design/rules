# Prism instance identity, grouping, and undo references

Directory identity, UUID lookup, display labels, live grouping, saved grouping, filesystem effects, and undo references have different meanings. This band executes 24 selected unchanged method bodies with Qt 6.12 Core and private files. Its 24 scenarios include 23 current-source scenarios and one separately identified canonical-key candidate. It does not execute the full Prism application or qualify its GUI, watcher, real settings backend, OS trash, accounts, or games.

The [source ledger](../sources/prism-library-selections.json) records four files retrieved from the fixed `7d2d3c1ec6fcf8255ebacd02d9f792688575dfb4` raw-source URLs. The [native receipt](../evidence/prism-library-20261125T092450586460Z/receipt.json) binds the original method excerpts, generated source, candidate, compiler, Qt framework, shared extractor, binary, and producers. The [exact release-status check](../evidence/prism-library-20261125T092450586460Z/release-status.json) is separate from source/binary qualification. These byte identities do not establish a reproducible packaged Prism build or independent membership in the release Git tree.

The fixture compiles in 2.297 seconds and executes in 0.333 seconds. Both owned process groups are absent, and the independent process search finds no reference to its private workspace. About 1.1 MiB of source, binary, files, and failure evidence remain. It uses QCoreApplication only, with no desktop lease or graphical window.

## What the adapters establish

The selected `InstanceList` and `BaseInstance` method bodies are unchanged. The fixture supplies a BaseInstance-shaped object, synchronous in-memory settings, signal/watch adapters, and filesystem wrappers restricted to its private root. The trash adapter renames into another private directory; it never calls the operating system's trash. Reads/writes and occupied-target rename failures use real Qt/filesystem operations. Injected trash, delete, and write refusals are labeled controls, not claims about the full production filesystem helper.

The constructor, object loading, real INI persistence, actual notification delivery, watcher refresh, shortcuts integration, and normal UI callers remain unqualified. In particular, source methods that emit `instancesChanged()` do not trigger a real launcher reload in this fixture. A path-renaming prefix or immediate stale object therefore cannot be presented as a full GUI failure.

## A UUID lookup is not a canonical group key

`BaseInstance::id()` returns the directory basename. Its UUID and display name are separate fields. `setName()` changes the display name; it does not rename the directory. The native controls allow duplicate display labels while retaining different directory/UUID identities. A different role passed to `setData()` is refused without changing the label. Real label persistence is outside the in-memory backend's evidence.

`getInstanceById()` accepts either directory ID or UUID and returns the first matching object. If one object's UUID equals a later object's directory ID, the earlier UUID match wins. The fixture constructs that overlap using valid-shaped synthetic UUIDs; it does not claim that Prism's own copy workflow creates it. Instance creation, UUID uniqueness policy, external copying, and full callers still need review.

`setInstanceGroup()` resolves its argument to an instance, then looks for an existing slot under the canonical directory ID. Updating that slot works. When the slot is missing, however, the insertion uses the original argument string. A first assignment through a UUID is therefore stored under the UUID. `getInstanceGroup()` reads the directory key, while saving filters against discovered directory IDs.

| Control | Live index after assignment | Effective group for A | Saved membership |
| --- | --- | --- | --- |
| First assignment through directory ID | `a → New` | New | A in New |
| First assignment through UUID | `uuid-A → New` | Ungrouped | No saved group |
| UUID assignment with an existing canonical slot | `a → New` | New | A in New |
| Private canonical-key candidate | `a → New` | New | A in New |

This is a method-level asymmetry between resolution, mutation, and persistence. Normal GUI reachability with a UUID argument has not been established. The private candidate changes only the missing-slot insertion to `inst->id()` and repairs that fixture. It is not a product patch.

Preserve the existing directory-keyed group format for this correction. The lookup projection retains the two matching candidates; the fixture's unrelated B does not match and is omitted from that model input. A more explicit future lookup can distinguish directory and UUID selectors and report ambiguous matches, while retaining today's first-match string helper for callers that require it. Do not silently reinterpret old group keys as UUIDs. Replacing all instance identities would be a different storage/API change with a much larger compatibility obligation.

## Refused filesystem work can still change saved grouping

Both trash and permanent-delete methods remove the group assignment and save the group list before invoking their filesystem helper. In the injected refusal controls, the original directory and its payload remain, but both live and saved grouping have already become empty. Trash returns false; permanent deletion returns void and logs the failure.

This establishes the selected ordering and partial effects under a no-filesystem-effect refusal. The real filesystem helpers can have different partial effects, so false must not be generalized to “the directory is unchanged.” Actual GUI fallback, user confirmation, logs, watcher updates, and crash behavior remain separate obligations.

A useful result should retain the instance/group basis, known filesystem effects, saved-metadata outcome, and a safe next action. Avoid a blanket failure headline that implies no effect occurred. Moving the metadata write later alone does not solve every partial filesystem failure; preserve the prior relationship and explicit uncertainty until reconciliation is possible. A typed internal result could coexist with the old void/Boolean wrapper, while the GUI deliberately adopts richer feedback.

## Undo can discard its retry reference before restoration

`undoTrashInstance()` pops its history entry before choosing a destination or attempting the main rename. It appends `1` while the original target is an existing directory. An existing regular file does not enter that loop, and QFile then refuses the occupied-target rename.

The native regular-file collision returns false with the original payload still in the private trash directory. The history stack is already empty. A second call returns true because there is no history, while the payload remains unrestored. This is loss of the application's retry reference, not observed deletion of the payload. The empty-history success also needs to remain distinct from an actual completed restore.

The shortcut control restores the main instance but cannot replace an occupied shortcut path. It returns false after that partial success and also has no retry entry. Retaining history only until the main rename succeeds would therefore leave the shortcut boundary unresolved.

The [proposed retry model](Library.lean) retains separate main and shortcut obligations. It cannot forget its reference after a failed main restore or an incomplete shortcut restore. Once the main item is restored, a retry addresses only remaining shortcuts rather than attempting the main move again. These are model-only candidate rules. The forgetting predicate covers obsolete main/shortcut retry references only; unsaved group metadata and partial-effect diagnostics need their own retained owners. A history reference does not exclusively retain OS trash contents or authorize overwriting a destination: every later attempt must revalidate source availability, target identity, and collision policy.

An additive undo result could distinguish no work, complete restore, partial restore, and failure, naming the actual destination ID and remaining items. Keep the existing Boolean method as a compatibility wrapper if needed. Changes to the private in-process history need no on-disk migration by themselves; this study does not propose persistent trash ownership or promise recovery after application restart.

## Collector error and independent postimages

The original collector's `restoredPath` field chose the first existing directory. In the directory-collision scenario, that was the empty occupied `a` directory, although the payload was restored to `a1/data`. The [read-only review](../evidence/prism-library-20261125T092450586460Z/postimage-review.json) preserves the original value and verifies the actual bytes independently. That field is excluded from model authority, with a control confirming that changing it cannot override the postimage evidence.

The maintained collector now checks payload identity. Its corrected C++ route has passed a separate syntax check; it has not been natively recollected. Original producer, source, rows, and binary identities remain unchanged. This is a fixture correction, not a Prism defect.

In that same scenario, the helper's live group index contains `a1 → Old`, but saving filters `a1` because the fixture's last discovered set still contains only A/B. The saved group file is empty. This demonstrates the dependence on discovery basis and operation order in the selected prefix. Real signal/watcher sequencing, refreshed objects, later saves, and full GUI persistence must be joined before claiming an end-to-end group-restoration bug.

## Loading, saving, and discovery preserve different observations

The remaining controls expose these distinctions:

- Group rename merges both memberships and transfers a collapsed marker; deleting a group removes assignments without deleting the instance directories.
- Loading counts every raw member, while the assignment map keeps one value per ID. A duplicate member produces count two but one binding; saving deduplicates membership through QSet.
- Unknown member IDs can remain in the loaded map/counts but are filtered from a save against the known instance set. Full discovery coverage matters before deciding what is missing.
- Loading new hidden=false metadata does not clear existing collapsed markers. This is a repeated-helper observation; full folder-switch/reload behavior remains unqualified.
- Unsupported format metadata leaves the previous live mapping untouched on load. A later explicit save in this fixture still emits format `1`; load refusal alone is not a guarantee against overwriting unsupported metadata.
- An unprobed list deliberately skips saving. An injected write failure also leaves the old file while live grouping changes, but for a different reason. The source APIs return void at those points; the replay's cause labels are fixture/source classifications, not a measured public result enum.
- Discovery includes hidden configured directories and the fixture's alias to an outside private directory, while excluding an alias into a sibling instance. This is selected-root discovery policy, not a filesystem sandbox or permission to delete an alias target.
- `syncInstanceDirName()` can move a directory without changing the existing object's root. Reload/caller coordination is necessary; the immediate stale object is not a demonstrated full rename-workflow failure.

Preserve the existing incomplete-discovery save gate and no-overwrite behavior. A clearer store model could retain loaded assignments, unresolved references, effective discovered membership, collapsed UI state, and saved-image status separately, deriving counts where appropriate. Tolerance of duplicate/unknown records and unsupported versions needs an explicit policy decision before changing visible groups or discarding metadata. No migration framework is selected.

For UI feedback, distinguish a changed live group from a saved group, and an instance restored with remaining shortcuts from an entirely failed restore. The inspected helpers log errors, but the complete caller/notification path was not executed. Reuse existing launcher feedback and refresh mechanisms before adding a generic transaction service or another event bus.
