# Executables, named scripts, and package commands

This band compares npm 11.20.0 with shipped libnpmexec 10.3.3, pnpm 12.21.0, and Yarn Modern 4.19.0 on macOS arm64/Node 26.13.1. It investigates what `exec` means and which program runs when an installed package binary, an inherited `PATH` command, and a named root script share a name. The commands legitimately have different targets; this is not a reproduced executable-resolution defect.

The [source ledger](../sources/js-exec-selections.json) records actual shipped npm module identities and pinned pnpm/Yarn source. Those are selected-version/source correspondences, not reproducible-build claims. Native observations cover literal command names, one known dependency binary, generated programs, and private installed contexts. Full package acquisition, shell parsing, and other hosts remain open.

## Observed command meanings

| Interface                                                    | Meaning in the selected implementation                                                                        | Result with only the owned inherited `PATH` program available                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `npm exec --offline --yes=false -- rules-exec-probe …`       | Package command with local/package/global fast paths; otherwise resolve the requested package.                | Exit 1 with `ENOTCACHED`; the inherited program does not run.                                     |
| `npm exec --offline --yes=false --call 'rules-exec-probe …'` | Explicit shell command in the npm execution environment, with no requested package in this fixture.           | The inherited program runs successfully.                                                          |
| `pnpm exec rules-exec-probe …`                               | Resolve a program against the extended project `PATH`, then pass its argument vector; shell mode is separate. | The inherited program runs successfully.                                                          |
| `yarn exec rules-exec-probe …`                               | Portable shellcode in the installed project environment, with arguments supplied separately.                  | The inherited program runs successfully.                                                          |
| `<manager> run rules-exec-probe …`                           | Select the declared package script of that name.                                                              | Separately tested with a dependency binary present: the root script runs rather than that binary. |

Npm's selected `libnpmexec` first considers local package `bin` declarations, ancestor `node_modules/.bin`, and configured global paths. Without a matching fast path, the supplied name becomes package intent. The selected source calls package-manifest resolution before its later installation-confirmation path. `--yes=false` is not evidence of no catalog lookup. The native fixture is offline with an empty private cache and global prefix; it does not establish online request, confirmation, or download behavior. The explicit `--call` fixture uses a complete controlled shell snippet and no separate positional command; that interface rejects combining `call` with nonempty command arguments.

Pnpm's default is a program plus arguments; `--shell-mode` explicitly selects a different verbatim shell-string path. Yarn's `exec` is already shellcode: the source restores project state, creates wrappers for accessible binaries, and invokes the portable shell. Similar outcomes for one literal command do not make their parsing or authorization models interchangeable. Names and argument vectors need separate representation from executable shell snippets.

## Collection and evidence

The [collector](probe.py) uses nine fresh offline projects: three per manager, with a dependency plus inherited program, only an inherited program, or neither executable. All projects still declare a named script with the tested name. One generated local archive supplies the dependency; generated root and `PATH` programs identify themselves and write an independent JSON event. Private home, configuration, cache, store, temporary directories, and npm global prefix isolate the work. No global package installation, registry service, or existing project is used.

The [receipt](../evidence/js-exec-20261125T011635281573Z/receipt.json) records 27 commands: nine installation baselines and 18 subsequent exec/run/call operations. All owned groups retired. Generated work measured 8,416 KiB. Thirteen recorded invocations preserve the exact Unicode, space, semicolon, and flag argument strings and the actual requested working directory. Every manager's nested `exec` runs in the invocation subdirectory. This does not test a named script invoked from a subdirectory; the research decoder refuses that unqualified case.

When both dependency and inherited programs exist, all three default `exec` commands run the dependency binary. Named `run` selects the root script. With neither executable present, that declared script does not supply an `exec` binary: npm returns 1 for the offline package lookup, pnpm returns 1 for program lookup, and Yarn returns shell status 127. Npm's explicit missing shell command also returns 127. Identical status 1 therefore cannot identify the failing phase without the diagnostic and request context.

The [read-only checker](observations.py) binds exact command streams, process records, authored and lock images, appended events, and the independent program stdout. It checks the [retained generated archive](../evidence/js-exec-20261125T011635281573Z/fixture-executable-1.0.0.tgz) without extracting it, plus nine [input readbacks](../evidence/js-exec-20261125T011635281573Z/project-inputs.json). Those readbacks were collected afterward and match captured authored hashes; installed program hashes are post-collection witnesses, not a recorded hash at every earlier execution boundary. Source modules are checked against their retained digests and, for npm, the selected installed files.

The frozen first producer includes `managePackageManagerVersions: false` in pnpm configuration. This Rust pnpm warns that it does not recognize the setting and ignores it. That was a fixture mistake, not a product defect or a working isolation guard. The maintained collector removes it for future runs; the frozen producer, warnings, and observed outcomes remain unchanged. Direct pinned invocation, absence of a `packageManager` field, and private roots are the actual controls. No completed native workflow was repeated to hide the warning.

After installation, all measured authored and lock bytes are unchanged. The generated programs write only their private event files in this profile. Cache/log/temporary and general child-program effects are separate; a successful resolution does not constrain arbitrary executable behavior. Yarn uses the explicitly selected node-modules linker and disabled install scripts, while explicit invocation of the generated program remains allowed. This is not general PnP, script-trust, or process-sandbox qualification.

## Models, reporting, and design

The [Lean](Exec.lean) and [Bend](Exec.bend) models preserve separate interface meaning, selected target, lookup phase, status, requested directory, and argument vector. Twelve Lean and nine Bend laws include npm's package-versus-shell distinction, dependency precedence in the fixture, named-script separation, and different missing-command phases/statuses. The named-script projection assumes an admitted declaration at project root; arbitrary script selection is not modeled here.

The [pure replay](conformance.py) compares all 18 post-install operations, including the thirteen exact native argument/directory events and five failures. Failure phases are source interpretations bound to checked diagnostics; the models do not reconstruct package resolution or run a shell parser. Thirteen malformed or out-of-profile inputs refuse; five changed outcome fields are detected. A restricted line codec frames only the Bend research driver, not user arguments or a proposed public API. The [conformance receipt](../evidence/js-exec-20261125T011635281573Z/conformance.json) retains comparison inputs, outputs, source premises, and hashes. Replay runs no package manager, Node process, or fixture executable.

Keep the current command distinctions. Pnpm's explicit program-versus-shell mode is useful; Yarn's shell-oriented interface and npm's package-command acquisition also have valid purposes. Unifying their command spellings or adding a universal implicit fallback would change their domain meaning. Npm callers who want an existing shell command already have `--call`; documentation and errors should make that route visible when package lookup was not intended. Preserve installation confirmation as a separate event from metadata lookup.

For application APIs, retain the existing distinctions as explicit request data: package command and acquisition policy, program plus argument vector, shell snippet and interpreter, or declared script and package context. A result should preserve the selected binary/script/package, requested and effective working directory, interpreted failure phase, child status when one ran, and scoped effects. This can reuse current options, bin maps, project context, and typed spawn errors. It does not require a new universal resolver, parser, or execution framework. Keep arbitrary child output and side effects outside the resolver's promises.

Two small interface inconsistencies deserve separate consideration. Yarn's selected `exec` usage describes the active workspace's root directory, while its source and native nested case preserve the supplied invocation directory. Clarify the usage around project environment versus actual working directory. Pnpm's nonrecursive missing-program diagnostic retains `ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL`; the human cause is already useful. Preserve stable machine codes unless a versioned interface change is selected, and keep the actual command scope separate from that historical identifier. The ignored-setting warning was useful and should remain, with the fixture corrected instead.

For empack's current/native and portable design, distinguish rendering a launch command from requesting program execution or authorizing package acquisition. An editable source, saved plan, generated shell script, and structured subprocess request have different meanings. Carry program/arguments, runtime, directory, environment, captured basis, and capability admission through their existing ownership boundaries; do not convert imported package metadata into arbitrary launch commands. These are design constraints and proposals, not production changes from this study.

Further obligations include online or cached package acquisition, confirmation, root/self/global bins, collisions and ambiguous metadata, permissions, failed/long-lived children, cancellation, PnP, workspaces, recursive scheduling, inherited environment policy, arbitrary quoting/shellcode, interactive use, Windows, and races between lookup and execution. The literal-argument successes do not establish a shell-injection vulnerability or a universal escaping guarantee.
